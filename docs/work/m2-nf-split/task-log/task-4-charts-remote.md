### Key Decisions

— session 2026-09-17

- **Exposed module `./capability` with the named export `capability`**, not the plan sketch's
  `./capabilities` / `chartsCapability`. Task 3 fixed the string as `CAPABILITY_MODULE` in the
  loader and documented it on `AgentCapability`; the sketch predates that. Shell specs import
  `capability as chartsCapability`, so each fixture change stays one line. (Approved in the briefing.)
- **NF remote name `charts`, not the project name `mfe-charts`.** The orchestrator registers a
  remote under the `name` in its `remoteEntry.json`, and `loadRemoteModule(name, …)` looks it up
  by that name — with the schematic's `name: 'mfe-charts'` the shell logged
  `Remote 'charts' is not initialized` although the manifest said `charts`. The NF name, the
  manifest key, the `?capabilities=` token and the capability's `name` field are now one word;
  the Angular project keeps `mfe-charts` (folder, port, targets). Found by the production probe.
- **Sharing: the schematic's `shareAll` mirrored from the shell, not the plan's explicit list.**
  With `ignoreUnusedDeps` (default) the remote's `remoteEntry.json` lists only what the exposed
  module's graph imports: `@angular/common` (+`http`), `@angular/core` (+ secondaries),
  `@a2ui/angular/v0_9`, `@a2ui/web_core/v0_9` (+`basic_catalog`), `rxjs`, `rxjs/operators`,
  `tslib`, `zod/v3`, `zod-to-json-schema` — the plan's list minus `@copilotkit/angular` and
  `@ag-ui/*`, which the remote never imports. One config shape for host and remotes; the policy
  for host-only packages stays with Task 6. (User: "shareAll ist fein, dann die Shell auch so" —
  the shell already was.)
- **`zod` (the root zod 4) is no longer shared; `zod/v3` still is.** Root cause, found by the
  probe and present since Task 3: every a2ui, ag-ui and CopilotKit package carries a nested
  `zod@3.25.76`; in the monolith esbuild resolved their `from 'zod'` to that copy. NF's
  `shareAll` shared the root `zod@4.4.3` and rewrote those imports to the v4 classic entry, so
  web_core's `ActionSchema` became a v4 schema nested inside our v3 catalog objects, and every
  `updateComponents` died in v3's `ZodObject._parse` with `k._parse is not a function` — for
  maps alone as well, i.e. with no remote involved. Task 3's probe only rendered the chat page,
  which processes no surface until the agent answers. `skip: ['zod']` matches exactly, so the
  secondaries `shareAll` discovered under `zod` (`zod/v3`) stay shared; each package chunk now
  bundles its own nested zod 3 again, our schemas and `zod-to-json-schema` use the one shared
  `zod/v3`, and the shell's own root-`zod` consumers (the CopilotKit tool definitions) are bundled
  into the app chunk. Alternatives rejected: mirroring `ActionSchema` in `zod/v3` (T4-AC-04
  forbids any change to the serialized schema, and web_core's own message validation would still
  run on v4 in the browser and v3 under Node); `ignoreUnusedDeps: false` (unrelated); an explicit
  `share({ 'zod/v3' })` (unnecessary, see skip semantics).
- **`@angular/common` shared with `includeSecondaries: { keepAll: true }` in the remote.**
  Unused-dependency pruning analyses the federation tsconfig's `files`, which the builder sets to
  the exposes; the standalone bootstrap is not in that graph, so `@angular/platform-browser` is
  inlined into the remote's bootstrap chunk, and its (dead, hydration-only) import of
  `@angular/common/http` had no import-map entry when the remote ran alone
  (`Unable to resolve specifier '@angular/common/http'`). Sharing `@angular/platform-browser`
  instead is not an option (corrected later this session, see the keepAll semantics below).
- **Markdown renderer wired statically in both hosts.** The a2ui `DefaultMarkdownRenderer`

— session 2026-09-17 (follow-up questions on sharing semantics, probed by build)

- **`keepAll` widens "used" from the entry to the package; it never forces an unused package.**
  `removeUnusedDeps` keeps an entry with `includeSecondaries` when *any* import of that package
  (primary or secondary) exists in the analysed graph, otherwise only when the exact entry is
  imported. Consequences, each confirmed by a probe build of the remote: an explicit
  `'@angular/common/http'` override without the flag is pruned again; the same override with
  `keepAll` survives (identical result to the override on `@angular/common`, since the default
  skip list drops the other secondaries anyway); `keepAll` on the unused primary
  `@angular/platform-browser` shares nothing — the package is not imported by the exposed graph,
  so it and `@angular/common/http` are both pruned. The only way to share a package the exposed
  graph never imports is `features.ignoreUnusedDeps: false` for the whole remote; NF has no
  per-entry force option. The analysed graph is the exposes plus the imports of the shared
  packages reachable from them (that is why `@angular/common` is declared: `@a2ui/angular`
  imports it), never the standalone bootstrap.
- **`ignoreUnusedDeps: false` on the host (user question) is a Task 6 policy option, not a
  Task 4 change.** It would share every declared dependency and secondary (here mostly ~20
  unused `@angular/cdk/*` entries and `@a2ui/markdown-it`), growing the shell build and the
  import map without downloads; it would have prevented the host's markdown pruning, not the zod
  rewrite and not the remote's standalone gap. A remote cannot rely on it anyway: a host only
  provides what its own `package.json` declares, and the demo's claim is repo-portable remotes.

— session 2026-09-17 (ngDevMode guard)

- **The `ngDevMode ??= false` guard is removed from both `main.ts` files; supersedes Task 3's
  decision to carry it over from the reference project.** Origin: the demo added it in its
  Task 11 (2026-05-10) after `ng build` → `ng serve` without clean crashed the shell's own code
  with `ngDevMode is not defined` — a prod-built shared `@angular/core` chunk had been loaded
  into the dev session, and a prod chunk never initializes the global that dev-built app code
  reads. The demo's own log names the `clean` script as the root-cause fix and the guard as a
  guardrail. Both NF cache fixes for mixed modes (`dev=` in the checksum, separate `-dev` meta
  files) were already in the demo's core 4.1.3 (released in 4.0.0), so how the prod chunk got
  into the import map is unexplained; the crash has never been observed in this repo. Cost:
  Angular reads a pre-set `false` as prod mode (`initNgDevMode` returns false, `isDevMode()`
  false, no perf counters, no dev assertions). With adapter 21.2.12 the shared dev chunk of
  `@angular/core` carries no `ngDevMode` define and reads the global, so the guard switched dev
  mode off in every clean dev session of this repo (Node probe in Test Evidence). In the demo
  the adapter 21.2.1 compiled `ngDevMode: 'true'` into the dev chunk, which is why the guard was
  harmless there. Rejected alternative: `if (typeof ngDevMode === 'undefined') ngDevMode = true`
  — prod-inert (the CLI defines the identifier as `false` in prod builds) and dev-mode
  preserving, but machinery for a failure this repo has not seen; `npm run clean` stays the
  remedy, and the core's own error names the cache folder when a recorded artifact is missing.
  User decision after the analysis.
